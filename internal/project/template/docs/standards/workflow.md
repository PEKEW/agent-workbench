# 工作流规范（agent 与人共用）

本规范回答：接到一个任务后，按什么顺序做事、什么时候停、凭什么算完成。
编码风格见 `coding.md`，评审标准见 `review.md`，文档写法见 `writing.md`。

## 流程（六步，按序执行）

1. **先计划，后编码**。复杂任务（多文件、新特性、架构决策）先由 reasoning model 出书面计划并获确认，再动手。单行修复、明显的 typo 类任务直接执行。
2. **前置问题立即暂停报告**。发现前提不成立（依赖缺失、上游数据错误、spec 自相矛盾、任务描述与现实不符）时，停下来说明情况，不硬闯、不编造绕过方案。暂停是规范行为，不是失败。
3. **复杂任务先写中止条件**。开工前用一句话写明「出现什么情况就停下来问人」（例如：「修改超过 N 个文件」「需要改 spec」「数值结论与旧数据方向相反」），写在 progress.md 当次记录里。
4. **长任务及时保存依据**。`../../progress.md` 只保存精简进度、里程碑与下一步；详细验证和阶段性结果写入 `../reviews/` 或任务产物，原始运行日志由本地服务保存。当前状态和接续入口写入 `../../PLAN.md`。
5. **只碰被要求碰的东西**。发现任务外的问题，记录到 PLAN.md 的「打开的决策点」或对应 review 文件，不顺手修。
6. **完成 = 证据，不是「看起来完成」**。收尾前按任务类型出具至少一项证据：

| 任务类型 | 最低证据 |
|---|---|
| 代码修改 | 相关测试通过日志 + 改动文件的静态检查（ruff/mypy 可用时） |
| 数值/实验 | 结果文件（JSON/CSV/图）+ 与基准或理论值的对照说明 |
| 指标/可视化 | 截图或输出图片，且本人看过内容（不是只确认文件存在） |
| 文档 | 文中引用、命令、路径经实际验证存在/可运行 |
| 修复 bug | 修复前后对照数据 + 回归验证（原场景不再复现） |

## 会话收尾检查（每次会话结束前）

1. progress.md 已更新必要的里程碑与接续入口，保持 100 行以内；详细记录放入对应证据文件。
2. 路线或决策发生变化时，同步更新 `../../PLAN.md` 与 `../task_plan.md` 决策日志。
3. 引用过的文件路径仍然有效（移动文件后 grep 一遍）。

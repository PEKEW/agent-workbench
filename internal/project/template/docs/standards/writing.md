# Markdown 写作风格

本规则适用于项目中的持久化 Markdown 文档。完整规范和更多示例见
`docs/standards/writing.md`。

## 核心规则

1. 使用标准术语。已有通用说法或项目既定术语时，不另造表述。
2. 不使用比喻。直接说明对象、过程、现象和结果。
3. 表头、分类名和状态标签使用中性表述，如“问题”“现象”“影响”“结果”“已确认”“结论待定”。
4. 避免“是 X，不是 Y”的对比句式，直接陈述得到证据支持的结果。
5. 表格和列表条目只需完整表达当前信息，不强制每条包含数字、解释或结论。
6. 原因尚无证据支持时写“原因未查明”或“该关系尚未验证”，不补充推测。
7. 不使用口语、夸张、情绪化或宣传性表述。
8. 不使用拟人表述，直接描述模型、指标、信号、算法或数据的行为和统计性质。

## 高频术语

优先使用以下表述：

- 超长度、超不超长度：截断、是否触及长度上限
- Ray 的端口会跟自己撞：多个任务的 Ray 抢占同一端口
- 臂：方案
- 只看长度那条线：长度启发式基线
- 刷奖励：奖励被优化，但评测指标未改善
- 存档：checkpoint
- 血统：基座来源
- 坑：问题
- 代价和教训：影响
- 把握：确认程度
- 怎么做的：实验设置
- 还在跑的：进行中
- 白跑、白占：无效运行、空占
- 致命问题：主要问题

## 表述要求

- 区分实验设置、观察结果、已确认结论、解释、限制和开放问题。
- 结论强度不得超过现有证据。
- 同一概念、状态和分类在全文中使用统一表述。
- 删除无信息量的过渡句，直接进入实验设置、结果或分析。
- 局部修改不得扩展到无关段落。
- 保持代码块、行内代码、路径、命令、公式、引用、数字、单位和配置名称不变。

## 完成前检查

检查修改内容是否存在：

- 非标准术语或临时创造的说法；
- 比喻、口语或拟人表达；
- “是 X，不是 Y”结构；
- 不统一的表头、分类名或状态标签；
- 未经验证的原因解释；
- 强于证据的结论；
- 为保持形式一致而补充的无依据内容；
- 重复结论或无信息量的过渡句。

## 适用范围

本规范适用于项目中的持久化 Markdown 文档，包括：

- `README.md`
- `PLAN.md`
- `progress.md`
- `docs/specs/`
- `docs/reviews/`
- `docs/standards/`
- `docs/findings.md`
- 实验报告、状态说明和技术分析文档

修改现有文档时，应保持该文档原有的语言、术语、标题层级和组织方式。

以下内容除非任务明确要求，否则保持原样：

- 代码块和行内代码
- 文件路径和命令
- 函数名、类名、变量名和配置项
- 数学公式
- 链接和引用
- 数字、单位和统计结果
- checkpoint 名称
- 数据集、模型和方法名称

## 核心规则

### 1. 使用标准术语

优先采用领域内已有的通用术语。已有标准说法的概念，不另造表述。

同一概念在全文中使用同一术语。术语已经在设计规范或前文中确定时，不随意更换同义表达。

| 原表述 | 规范表述 |
|---|---|
| 超长度 | 截断 |
| 超不超长度 | 是否触及长度上限 |
| Ray 的端口会跟自己撞 | 多个任务的 Ray 抢占同一端口 |
| 臂 | 方案 |
| 只看长度那条线 | 长度启发式基线 |
| 刷奖励 | 奖励被优化，但评测指标未改善 |
| 存档 | checkpoint |

### 2. 不使用比喻

直接说明对象、过程、现象和结果。不得要求读者根据比喻推断实际指代。

不把临时比喻固定为术语。表达可以简洁，但指代必须明确。

| 原表述 | 规范表述 |
|---|---|
| 血统 | 基座来源 |
| 8 个不同血统 | 8 个不同基座的模型 |
| 那是尺寸差异，不是血统差异 | 原有区间由 Qwen 的 14B、32B 和 72B 模型构成，差异来自参数量 |
| 已经吃掉一半空间 | 已覆盖一半区间 |
| 变成了一个认题目的检索器 | 退化为问题识别，与学习价值无关 |
| 挑出来的题目看上去健康得多 | 选中问题的截断比例更低 |
| 误差范围还盖着基准线 | 置信区间与基线重叠 |

### 3. 表头、分类名和状态标签使用中性表述

表头和分类名使用能够直接说明内容的中性名词。

优先使用：

- 问题
- 现象
- 影响
- 结果
- 实验设置
- 确认程度
- 当前状态
- 取值数量
- 重合率

| 原表述 | 规范表述 |
|---|---|
| 坑 | 问题 |
| 代价和教训 | 影响 |
| 把握 | 确认程度 |
| 怎么做的 | 实验设置 |
| 重挑一次还剩多少重合 | 重采样后的重合率 |
| 有几种不同取值 | 取值数量 |
| 还在跑的 | 进行中 |
| 一个必须关掉的开关 | 需要关闭的过滤器 |

#### 状态标签一致性

章节、表格和列表中的状态标签应保持一致。

推荐使用：

- 已完成
- 已确认
- 进行中
- 未达到基线
- 结论待定
- 原因未查明
- 需要修正
- 尚未验证

不要在后文改用口语化或带评价色彩的标签。

| 非规范标签 | 规范标签 |
|---|---|
| 做通了 | 已完成 |
| 意外发现 | 已确认，或结论待定 |
| 需要修 | 需要修正 |
| 没有买到想要的 | 未达到预期结果，或未达到基线 |

状态标签应根据实际证据选择，不得用不同措辞重复描述同一状态。

### 4. 禁止采用“是 X，不是 Y”结构

不要依赖否定对照说明结论。直接陈述已经得到支持的结果、观察或差异。

| 原表述 | 规范表述 |
|---|---|
| 梯度对齐：是噪声，不是信号 | 梯度对齐：三项检查结果均在噪声范围内 |
| 我们买到了血统上的多样性，但没有买到能力上的多样性 | 新增模型覆盖了更多基座，但正确率均低于原有区间下界 |
| 考法和用法对不上 | 评测口径为成对比较，与实际使用方式不一致 |
| 稳定是靠粗糙换来的 | 取值数量少的指标具有较高重合率 |
| 越稳定的指标越挑不出东西，越挑得出东西的指标越不稳定 | 重合率与取值数量呈反向关系 |

表达差异时，应说明：

- 比较对象；
- 观测指标；
- 差异方向；
- 支持该判断的证据。

### 5. 不强制每个条目包含数字或结论

表格和列表中的条目只需完整表达当前信息。

部分条目可以说明：

- 实验设置；
- 已执行的操作；
- 观察到的现象；
- 尚未完成的步骤；
- 当前未知的信息。

不要为了保持形式一致而补充未经验证的解释、数字或结论。

例如：

> 对照组为随机选取的 32 个问题。

该表述已经完整。无需继续补充其他方案与对照组之间的关系，除非该关系已经得到验证并与当前内容直接相关。

### 6. 原因未查明时直接说明

尚无充分证据解释某个问题时，写：

> 原因未查明。

不得使用可能性推测填补证据空缺。

前文已经注明“原因未查明”时，后文不得继续补充未经验证的解释。

| 原表述 | 规范表述 |
|---|---|
| 这可能也解释了前文那个现象 | 该现象与截断的关系尚未验证 |
| 原因可能是模型已经学会识别题目 | 原因未查明 |
| 看起来与采样数量有关 | 采样数量与该现象的关系尚未验证 |

已经通过实验或分析确认的机制可以保留，但应明确说明证据来源和适用范围。

例如，第十章“后来查明了机制”之后的内容已经得到确认，可以按照现有结论保留。

### 7. 不使用口语词

使用准确、克制、可以直接验证的书面表达。

避免使用带情绪、夸张、随意评价或日常对话色彩的词语。

| 原表述 | 规范表述 |
|---|---|
| 赢得很干脆 | 差值为 0.030 |
| 测得更准 | 估计精度更高 |
| 测得更糙 | 估计精度更低 |
| 可选的余地很小 | 候选范围小 |
| 基本上等于抓阄 | 接近随机选取 |
| 本来就分不出高下 | 真实差距低于可分辨范围 |
| 白跑 | 无效运行 |
| 白占 | 空占 |
| 不是白捡的 | 需要 79 GPU·小时 |
| 一个致命问题 | 主要问题 |
| 有事后找补的嫌疑 | 该切分方式在观察结果之后确定 |

以下过渡句通常直接删除：

- 原因不复杂。
- 既然预测这条路走不通，那就退一步。
- 下面来看一个很有意思的现象。
- 值得一提的是。
- 显然可以看出。
- 不难发现。

删除后直接进入实验设置、观察结果或分析内容。

### 8. 不使用拟人表述

模型、指标、信号、算法、任务和数据不具有人的意图、能力或情绪。

直接描述其行为、输入、输出和统计性质。

| 原表述 | 规范表述 |
|---|---|
| 天生需要几百到上千次采样 | 该信号所需的采样量为几百到上千次 |
| 一旦超就制造出参差 | 截断发生时会增大奖励方差 |
| 24 步训练只挪动 0.05 | 24 步训练后正确率变化为 0.05 |
| 超得越彻底反而越稳定 | 截断率越高，奖励方差越低 |
| 回答内容本身的好坏参差 | 答案质量存在差异 |
| 模型偏爱较短回答 | 较短回答获得了更高奖励 |
| 指标看不见能力差异 | 该指标无法区分当前范围内的能力差异 |
| 奖励在鼓励截断 | 截断与奖励升高相关 |

## 表述优先级

出现多个可选表达时，按照以下顺序选择：

1. 项目设计规范中已经使用的术语；
2. 相关领域的标准术语；
3. 能够直接描述对象和现象的中性表述；
4. 必要且已定义的项目内部术语。

不得优先选择：

- 比喻；
- 口语词；
- 拟人表述；
- 带情绪或评价色彩的词；
- 为追求简短而产生歧义的表述；
- 未经定义的缩写；
- 根据当前结果临时创造的分类名。

## 证据与结论

文档应区分以下内容：

- 实验设置；
- 观察结果；
- 已确认结论；
- 可能的解释；
- 尚未验证的关系；
- 原因未查明的问题；
- 已接受的设计决策；
- 尚待决定的问题。

不得把以下内容写成已确认结论：

- 单次运行结果；
- 未完成的实验；
- 未进行复验的观察；
- 置信区间重叠时的确定性优劣判断；
- 观察结果之后提出但尚未验证的解释；
- 为当前结果临时选择的评价口径。

结论的确定程度应与现有证据一致。

## 段落和列表

- 每个段落表达一个主要内容。
- 段首先说明对象或结论。
- 后续句子提供证据、条件或影响。
- 相互平行的内容可以使用列表。
- 有先后关系的步骤使用编号列表。
- 不要把连续论证拆成大量短条目。
- 不要为了视觉对称补充无实际内容的条目。
- 相同结论只陈述一次。
- 后文需要引用前文时，使用明确的章节名、表号或实验编号。

## 表格

- 表头使用中性、明确的名词。
- 同一列中的内容应属于同一类型。
- 状态列使用统一状态标签。
- 数值列注明单位。
- 缺失结果使用“未测量”“尚未完成”或“原因未查明”，根据实际情况选择。
- 不使用模糊评价替代数值或观察结果。
- 条目可以只说明实验设置、现象或当前状态。
- 不为保持格式一致而添加未经验证的数字或结论。

## 修改范围

执行局部修改时：

- 只修改与当前任务有关的内容；
- 不为统一语气而改写无关段落；
- 不删除仍然有效的条件和限制；
- 不扩大原结论的适用范围；
- 不补充未经验证的因果解释；
- 不修改代码、路径、公式、引用、数字和单位；
- 不将历史观察写成当前结论；
- 不将评审意见直接写成已接受决策。

## 完成前检查

完成 Markdown 修改前，检查：

1. 是否使用了已有标准术语；
2. 同一概念的术语是否一致；
3. 是否存在比喻、口语词或拟人表述；
4. 是否存在“是 X，不是 Y”结构；
5. 表头、分类名和状态标签是否中性且一致；
6. 是否为了形式完整补充了未经验证的数字或结论；
7. 原因尚未确认时是否明确写为“原因未查明”或“尚未验证”；
8. 结论强度是否与证据一致；
9. 是否保留了代码、路径、公式、链接、引用、数字和单位；
10. 是否改写了与当前任务无关的内容；
11. 是否存在重复结论或无信息量的过渡句；
12. 是否存在前后矛盾的状态说明。

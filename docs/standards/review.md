# 评审规范

本规范回答：评审一段代码/一份实验时问什么、凭什么放行、如何反驳「看起来没问题」。
适用于人评审 agent、agent 评审 agent（rebuttal 流程）、agent 自查。

## 评审五问

1. **Correctness**：代码是否正确？边界条件、符号约定、单位、坐标系是否经得起一个反例？
2. **Design**：设计是否清晰、简单、可维护？接口是否表达意图而非实现细节？
3. **Complexity**：是否引入了不必要的复杂度？每一层抽象能否指出它消除的具体痛苦？
4. **Tests**：是否有足够证据证明行为正确？证据覆盖 Happy path 之外的情形吗？
5. **Maintainability**：未来的人是否能理解和修改？命名、注释、文档是否解释了「为什么」而不只是「是什么」？

## 简化原则

1. 能不用复杂架构，就不要用复杂架构。
2. 能用普通数据结构解决，就不要设计框架。
3. 能用明确规则解决，就不要依赖隐式约定。
4. 能用现有工具解决，就不要重新发明。
5. 能让新人读懂，就不要炫技。
6. 只碰你被要求碰的东西。

## 反合理化清单

评审中听到以下说法时，直接引用编号反驳。多 agent rebuttal 时同样适用。

| # | 借口 | 反驳 |
|---|---|---|
| E1 | 「测试都过了」 | 过的是哪些测试？覆盖 Happy path 还是边界？贴测试输出。 |
| E2 | 「改动很小，不需要验证」 | 小改动引起的事故最多。一行 diff 也要一行证据。 |
| E3 | 「之前是好的，我没动那块」 | 接口变了没有？全部调用方 grep 过吗？ |
| E4 | 「看起来输出合理」 | 「合理」的判据是什么？对照的基准、理论值或旧数据在哪？ |
| E5 | 「这个警告不影响结果」 | 证明是什么？警告路径上的数值差异量化过吗？ |
| E6 | 「性能以后再说」 | 记录在哪个文件里？没有记录等于已经忘记。 |
| E7 | 「文档后面补」 | 下一个进来的人怎么知道这件事？现在就写，哪怕三行。 |
| E8 | 「这段逻辑明显是对的」 | 「明显」省略了推理。把推理写出来，写不出来就是没验证。 |
| E9 | 「数值很小/很大，应该在误差范围内」 | 误差预算是多少？哪一步引入的？超过预算的尾巴怎么处理？ |
| E10 | 「这个词大家都懂」 | 「大家」是谁？第一次接触本项目的人不查其他资料能看懂吗？黑话与自造名词按 `writing.md` 表达硬规则判不合格。 |

## Rebuttal 流程

1. 评审方独立验证，不采信被审方的推导与测试代码（另写验证脚本、另做推导）。
2. 逐条判定：确认 / 部分确认 / 修正 / 驳回，各附证据。
3. 反合理化清单作为反驳引用库，编号引用。
4. 结论写入 `docs/reviews/`，命名 `<主题>_review_<日期>.md`。
